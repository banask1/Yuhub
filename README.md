# Yuhub

一个 Windows 系统工具箱，聚焦 **C盘清理**、**多线程下载** 与 **异地联机**。

> 当前版本 **v0.8beta**：首页已接入**本机配置检测**与**实时占用监控**，**C盘清理**与**多线程下载**已上线；v0.6 新增**系统托盘驻留**、**单实例限制**与**开机自启开关**；v0.9 恢复**异地联机**（内嵌 EasyTier 的「跨网房间」），**只保留异地联机这一种方案**，局域网直连（UPnP / 地址交换打洞）已按需求移除。侧栏为 5 项（首页 / C盘清理 / 多线程下载 / 异地联机 / 设置中心）。

## 功能特性

- **全自定义无边框窗口**：自绘标题栏（拖动移动 / 双击最大化）、边缘拖拽缩放
- **深色 / 浅色 / 跟随系统** 三态主题，选择结果持久化到注册表（`HKCU\Software\Yuhub\Yuhub`）
- **多分辨率适配**：高 DPI 感知（`PassThrough`）+ 窗口按主屏可用区域 72% × 82% 初始化，并限制在 780~1440 × 540~960
- **响应式布局**：功能卡片网格按视口宽度自动切换 3 / 2 / 1 列
- **可折叠侧边栏**：折叠后仅保留色块 + 图标，带 Tooltip
- **自绘组件**：方形滑块开关（带过渡动画）、分段选择器、Toast 提示、进度条、迷你趋势条
- **多线程下载**：分块并发抓取、下载前探测真实文件名与大小、实时速度 / 剩余时间 / 分块可视化
- **系统托盘驻留**：关掉窗口后程序仍在通知区域，单击图标恢复、右键菜单可退出（v0.6 新增）
- **单实例限制**：重复启动不会开第二个窗口，而是把已有窗口叫到前台（v0.6 新增）
- **开机自启开关**：设置页一键开/关，注册到 `HKCU\...\Run`，开机静默驻留托盘（v0.6 新增）
- **异地联机（内嵌 EasyTier）**：房主/成员身份切换，填同一组房间码+密码一键进入同一个跨网虚拟局域网；**房主固定虚拟 IP `10.126.126.1`、成员 `10.126.126.2`（可一键复制）、在线成员列表、切换 WiFi/热点自动关闭虚拟局域网**；无需 UPnP、无需自建服务器、免费（v0.9 恢复）
- **软件卸载**：列出本机所有已安装程序（含应用商店应用），调用各自卸载程序并**深度清理残留**的文件与注册表项（v0.10 新增）

## 主题包系统（v0.11 引入）

主题不再是写死在代码里的两组色板，而是**可插拔的主题包**，
存放在系统「文档」目录下：

```
C:\Users\<你>\Documents\Yuhub\
    YuUI\                  ← 默认主题（原来的「极简色块」，已更名 YuUI）
        theme.json         ← 色板，改这里就能改颜色
        theme.qss          ← 可选，自定义样式表模板
        preview.png        ← 可选，预览图
    如何自制主题.txt        ← 首次启动自动生成的使用说明
```

**首次启动会自动创建 `YuUI` 并写入完整色板**，视觉与旧版完全一致
（自检里做了逐键比对，确保零变化）。

### 怎么做一个自己的主题

设置中心 →「外观」只负责**切换**（模式分段器 + 主题下拉框）。

主题包请**手动制作**：复制 `YuUI` 文件夹，改名，然后改里面的 `theme.json`。
`theme.json` 支持**缺省合并**——只写你想改的键，其余自动继承 YuUI 的默认值：

```json
{
  "name": "MyTheme",
  "title": "我的主题",
  "dark":  { "accent": "#ff6600", "tile_1": "#ff6600" },
  "light": { "accent": "#cc5500" }
}
```

改完**重启 Yuhub** 即生效（启动时会重新扫描主题目录）。

> v0.8beta 起，设置页去掉了「另存为新主题」「打开主题目录」「重新扫描」三个
> 按钮与色板预览条，只保留切换功能。制作与查看主题请直接用资源管理器
> 打开「文档 / Yuhub」目录——说明见该目录下自动生成的 `如何自制主题.txt`。

### 设计上的几个取舍

* **主题目录用「文档」而不是程序目录。** 程序目录在 `Program Files` 下时
  普通用户没有写权限；「文档」始终可写，而且用户找得到、好备份。
  另外「文档」可能被重定向到 OneDrive 或别的盘，所以路径用注册表的
  `Shell Folders\Personal` 读取，而不是拼 `%USERPROFILE%\Documents`。
* **坏主题不致命。** `theme.json` 语法错误、缺 dark/light 一套色板、
  QSS 模板里写了非法 `$` 占位符 —— 这些都不该让程序打不开。
  读不出来的主题**跳过**，缺的色板**回退默认**，样式模板出错**退回内置模板**。
* **主题被删掉后自动降级。** 用户删掉正在用的主题文件夹，下次启动会
  自动落回 `YuUI`，而不是白屏或崩溃。
* **`ui/theme.py` 对外 API 不变。** `set_theme / current / build_qss / bus`
  全部保留，改的只是内部实现。所以 `main_window` 与所有页面无需改动，
  这次改动能控制在主题相关文件内。
* **下拉框箭头是运行时生成的 PNG。** 见下方「Qt 踩坑」一节。

### Qt 踩坑：下拉框（QComboBox）必须写全样式

顶部 `QWidget { background: transparent }` 是通配规则，会连**原生绘制的
复合控件**一起刷透明。`QComboBox` 中招后就是本次修的 bug：卸载页「按名称」
那个下拉框只剩一个深色底、文字几乎看不清。要写全三处：

1. `QComboBox` 本体 —— 底、边框、内边距、文字色
2. `QComboBox::drop-down` + `::down-arrow` —— 右侧箭头
3. `QComboBox QAbstractItemView` —— **弹出列表**（后代选择器，不是
   `QComboBox::item`），条目高亮用 `::item:hover` / `::item:selected`

**箭头不能用 CSS 的 border 拼三角。** `border-width: 5px 4px 0 4px` +
`width:0;height:0` 是经典 CSS 三角写法，但 Qt 的 `::down-arrow` 走的是
`QStyleSheetStyle` 的图片绘制分支，不按边框斜接规则渲染，实测画出的是一个
15×8 的实心矩形。**只能用 `image:` 指定图片。**

**`image:` 只认真实文件路径。** 实测（150% 缩放，裁图放大 8 倍逐像素看）：

| `image:` 取值 | 结果 |
| --- | --- |
| `url(data:image/svg+xml;base64,…)` | ❌ 什么都不画 |
| `url(file:///C:/x.svg)` | ❌ 什么都不画 |
| `url(C:/x.svg)`（裸绝对路径） | ✅ 正常 |
| PNG 文件 | ✅ 正常 |

而 `QImageReader` 本身能读 SVG，所以问题出在 QSS 的资源加载分支上。

**箭头颜色随主题变**（主题包是运行时扫描的），所以 `build_qss()` 会按当前
色板的 `text_dim` / `accent` / `text_faint` 生成三张三角 PNG，落到
`%TEMP%\yuhub_arrows\` 缓存，再以绝对路径写进 QSS。

**生成 PNG 时不能用 QImage/QPainter。** `build_qss()` 可能在 `QApplication`
创建之前被调用，此时构造 QImage/QPainter 会让进程**直接崩掉**（没有 Python
异常，退出码 127，非常难查）。所以 `_write_triangle_png()` 用 `zlib`+`struct`
手写最小 PNG，全程只依赖标准库。

> 注意区分两个概念：**明暗模式**（深色 / 浅色 / 跟随系统）与
> **主题包**（用哪套配色）。一个主题包同时提供 dark 与 light 两套色板，
> 两者是正交的：切主题包不会改变明暗模式，反之亦然。
> 设置页把两者分成两组控件（上面是模式分段器，下面是主题下拉框）。

### 图标

`resources/app_source.png`（1920×1920）是图标源图，`build_icon.py`
从它生成 7 个尺寸的 `app.ico`（16/24/32/48/64/128/256）。

有一个坑值得记：源图是**白底**不是透明底。直接用会在任务栏/开始菜单
带一圈白框（深色任务栏上格外难看）。所以 `build_icon.py` 做了
**从四边洪水填充的白底抠图**——注意不能用"把接近白的像素都变透明"，
那样会把锦鲤身体里的白色高光一起抠掉，图案出现空洞；只有与边缘连通的
白色才是背景。


## 本机配置检测（v0.2 新增）

首页顶部会显示当前电脑的配置，**完全离线运行，不联网、不上传任何数据**。

### 展示内容

| 区域 | 内容 | 数据来源 |
| --- | --- | --- |
| 设备分类标签 | 笔记本 / 台式机 / 一体机 / 服务器 | `Win32_ComputerSystem.PCSystemType` + `Win32_SystemEnclosure.ChassisTypes` + 电池存在性 |
| 设备型号 | 如 `Redmi G 2022` | `Win32_ComputerSystem.Product` / `Win32_ComputerSystemProduct.Name` |
| CPU | 型号 + 核心数 / 线程数 / 主频 | `Win32_Processor` |
| 显卡 | 型号 + 显存 + 当前分辨率 | `Win32_VideoController` + 注册表 `HardwareInformation.qwMemorySize` |
| 内存 | 总容量 + 条数 / 代数 / 频率 | `Win32_PhysicalMemory` + `Win32_ComputerSystem` |
| 硬盘 | **各盘盘号（C: D: E:）+ 逐个容量** | `Win32_DiskDrive` + `MSFT_PhysicalDisk` + `GetLogicalDriveStringsW` |
| 存储空间 | 逐盘列出：盘号徽标 + 占用条 + 已用/总计 + 可用 | `GetDiskFreeSpaceExW` + `GetVolumeInformationW` |
| 次级信息 | 系统版本 / 主板 / BIOS | `Win32_OperatingSystem` / `Win32_BaseBoard` / `Win32_BIOS` |

### 存储空间：逐盘容量（v0.4.2 新增）

「硬盘」区域不再只给一个总容量，而是**逐个盘列出并标注盘号**：

```
[硬盘]  C: D: E:      3 个盘 · 共 953.6 GB · 可用 599 GB

存储空间  共 3 个盘 · 合计 953.6 GB · 可用 599 GB
  [C:]  系统     ████████████░░░░░░░░   50.6 GB / 90 GB    · 可用 39.4 GB
  [D:]  软件     █████████████████░░░  303.8 GB / 386.6 GB · 可用 82.8 GB
  [E:]  移动硬盘 ░░░░░░░░░░░░░░░░░░░░  111 MB / 476.9 GB   · 可用 476.8 GB
```

- **盘号徽标**按占用率变色（≥90% 红 / ≥75% 琥珀 / 否则绿），一眼看出哪个盘快满了。
- 右侧同时给出**已用/总计**与**可用**，兼有比例和绝对值。
- 卷标有则显示卷标（如 `系统` / `软件` / `移动硬盘`），无卷标则显示固定/可移动。
- 只列真正有容量的盘，自动跳过空读卡器、光驱、网络盘。
- 盘容量是**即时数据**：用 ctypes 直调（`GetLogicalDriveStringsW` /
  `GetDriveTypeW` / `GetDiskFreeSpaceExW` / `GetVolumeInformationW`），
  毫秒级返回、不启动子进程、不联网，因此**缓存 profile 里也会重新取一遍实时值**，
  不会显示上次启动时的旧容量。

> 踩坑记录：占用条的底槽最初用了和行背景相同的 `surface_sunken`，
> 结果占用率低的盘（如 0% 的 E 盘）整条都"隐形"，看起来像没有进度条。
> 改用 `border_strong` 作为底槽色后，两种主题下都能看清空槽。

### 关键实现细节

- **设备分类采用三票制**：`PCSystemType`、`ChassisTypes`、电池存在性各投一票，出现任一"便携"信号即判为笔记本。游戏本常被 OEM 标成 `ChassisType=10`（Notebook），单看一项容易误判。
- **显存读取不用 WMI**：`Win32_VideoController.AdapterRAM` 是 32 位有符号整数，显存 >4GB 会溢出成错误值，因此改从注册表读 64 位的 `qwMemorySize`。
- **SSD/HDD 判定不用型号名**：很多 OEM 硬盘型号不含 "SSD" 字样（如 `FIREBAT FET34-512G` 实为 NVMe SSD），因此优先读 `MSFT_PhysicalDisk.MediaType`（3=HDD / 4=SSD）。
- **强制 UTF-8**：PowerShell 输出前设置 `[Console]::OutputEncoding`，避免中文系统上的 GBK 乱码。
- **不阻塞界面**：采集在后台线程执行（约 1~3 秒），结果通过 Qt 信号投递回主线程。首次启动即可见界面，硬件信息稍后填充。
- **结果缓存**：采集结果序列化到 `QSettings`，二次启动瞬间显示上次结果，同时后台静默刷新。
- **全项容错**：任何一项读取失败都不影响其他项，缺失字段显示 `--`。非 Windows 或 PowerShell 不可用时整体降级为提示文案。

## 实时占用监控（v0.3 新增）

首页下半部分是实时监控面板：**CPU / 内存 / 显卡** 三块指标，每秒刷新，各带一条 60 点的迷你趋势条（约等于最近 1 分钟走势）。

### 性能方案：为什么不用 PowerShell 每秒轮询

实测各数据源的耗时差距极大，直接决定了架构选型：

| 数据源 | 单次耗时 | 结论 |
| --- | --- | --- |
| PowerShell + CIM | **约 4270 ms** | 每秒刷新完全不可用 |
| ctypes 直调 Win32 API | **约 0.03 ms** | 快 10 万倍，用于 CPU / 内存快路径 |
| `nvidia-smi` | **约 240 ms** | 太慢，降频到每 2 秒一次并放子线程 |

因此采用混合架构：**CPU / 内存走 ctypes 直调**（`GetSystemTimes` / `GlobalMemoryStatusEx`），**显卡走 `nvidia-smi`** 后台线程低频采样，**磁盘容量每 5 秒**才读一次。

### 指标详情

### 关键修复

- **详情弹窗去掉系统白框**：改为 `Qt.FramelessWindowHint` + `WA_TranslucentBackground`，圆角与边框由内部 `DialogFrame` 提供，配自绘 `DialogHeader`（色块图标 + 标题 + ✕ + 可拖动）。彻底消除系统标题栏在深色主题下的白色违和感。

### 使用流程

**进入页面即自动扫描一次**（纯只读，只统计体积，不删任何文件），立刻就能看到可清理量。之后按需勾选（或点「全选安全项」）→ **清理选中项** → 二次确认 → 执行并汇总。清理完成后自动重扫，可直观看到剩余可清理量；重复进入页面不会打断你已有的勾选状态，想刷新随时点「重新扫描」。

### 安全设计（重要）

- **先扫描后清理**：扫描阶段绝不删除，只递归统计体积。
- **默认全不勾选**：由用户主动选择，不存在"手滑全删"。
- **二次确认弹窗**：明确列出项数与预估体积，标注「不可撤销」，需点红色按钮才执行。
- **危险项打标**：事件日志、驱动安装源等**级别 ≤1** 的项显示红色「不可恢复」标签，且**不会被「全选安全项」选中**。
- **不碰用户数据**：只清理明确的缓存/临时目录，不递归删除文档、桌面、下载等个人目录。
- **权限不足优雅降级**：无管理员权限时该项显示「需管理员」标签，其余项照常可清理，不整段失败。
- **保留目录本身**：清空目录内容而不删目录，避免破坏程序的运行期预期。
- **扫描/清理都在后台线程**：界面不卡顿，退出时线程正确回收。

### 验收方式（实测踩坑，很关键）

清理结果里的"已清理 XX MB"**不取自磁盘可用空间读数**，而是**真实被删除对象的体积合计**——删除前先把体积量出来、删完复查文件确实不存在，确认删掉才计入。

原因是实测发现：在部分环境（沙箱 / 文件系统重定向）下，**创建文件时可用空间立刻下降，但删除文件后可用空间不回升**。实测数据：
```
创建 40 MB  → 可用空间 -41,943,040 字节（读数灵敏，完全准确）
DeleteFileW → 可用空间          0 字节（文件确实消失，但空间不返还）
os.remove   → 可用空间   +1,044,480 字节（噪声级）
```
也就是说，任何基于"前后读数差值"的验收在这种环境下**恒等于 0**，会把"删了几百个文件"误报成"什么都没释放"。因此：

- `CleanResult.freed` = 真实删除的对象体积（结论口径）
- `CleanResult.removed_count` = 真实删除的对象个数
- `CleanResult.disk_delta` = 磁盘读数变化，**仅作诊断参考**，不作为结论

另外 `_rm_path()` 删除后会**复查文件是否真的不存在**——某些安全封装会静默拦截删除（`os.remove` 不报错但文件仍在），不复查会把失败误报为成功。同时 `_empty_dir_stats()` 统计的是**顶层条目数**（不是递归文件数），避免"清掉 4 个文件夹却报成 109 项"这种虚高。

### 文件占用处理

缩略图/图标缓存被 `explorer.exe` 持有，直接删会失败。参考 Dism++ 的
`<Activate Restart="Explorer">`，该规则**在删除确实失败时**会重启资源管理器释放占用，
然后重试——**不是无条件重启**（重启会让任务栏短暂消失，能不动就不动）。
显卡着色器缓存被驱动进程占用属正常现象（下次运行会自动重建），清理结果会如实报告"N 项被占用"。

#### v0.4.3 修复：清理时任务栏消失

用户反馈"清理完任务栏都没了，按 Win 键才回来"。根因是**资源管理器重启的竞态**：

```python
taskkill /f /im explorer.exe     # ← 返回只代表"杀进程请求已发出"，不代表进程已退出
time.sleep(0.6)
if "explorer.exe" not in tasklist_output:   # ← 此刻那个正在退出的 explorer 还在列表里
    Popen(["explorer.exe"])                 # ← 于是这行被跳过，没人拉起来
# 等它真正退出后 → shell 没了 → 任务栏消失 → 按 Win 键才触发系统恢复
```

修法分三层：

1. **等它真正退出再判断**：轮询进程快照直到 explorer 确实消失（而不是固定 sleep 一次）。
   探测用 ctypes 枚举进程快照（`CreateToolhelp32Snapshot`），不起子进程、不依赖
   `tasklist` 的本地化输出。
2. **保证结束时一定在运行**：等系统自动重启（`AutoRestartShell`）→ 超时未回来就主动
   `Popen(["explorer.exe"])` → 再等它起来 → 最后复核；复核失败再拼一次。返回值即"是否已恢复"。
3. **加退出兜底**：重启窗口内注册 `atexit` 钩子，万一本进程此时异常退出，也会把 explorer 拉回来。
4. **改成按需重启**：先直接删，只有确实有文件被占用时才重启重试。确认弹窗也会
   提前提示"任务栏会短暂消失 1~3 秒"。

回归测试（真机实测，每次真的杀掉 explorer）：

| 场景 | 结果 |
| --- | --- |
| `restart_explorer()` 后 explorer 仍在运行 | PASS（耗时 3.45s，PID 16508 → 5364） |
| 3 秒后再复核仍存活 | PASS |
| 普通规则清理（无占用） | PASS（explorer PID 完全未变，说明没有无谓重启） |
| 端到端清理缩略图缓存 30 项 / 5.01 MB | PASS（0 失败，explorer 前后均在运行） |
| 确认弹窗含"任务栏会短暂消失"提示 | PASS |

### 真机实测结果（本机）

自动扫描 **6.02 GB / 15 项**可清理。对其中等级最高（最安全）的 4 条规则执行清理：

## 多线程下载（v0.5 新增）

参考 PCL2「更多 → 百宝箱 → 下载自定义文件」的交互范式：
**粘贴链接 → 选保存位置 → 下载 → 实时进度 → 打开文件夹**。

### 使用流程

1. 粘贴下载链接（也支持点「粘贴」从剪贴板取，或回车直接开始）
2. 选中保存文件夹，文件名会从链接自动推断，可手动改
3. 选线程档位（低 / 中 / 高，默认中档），右侧实时显示换算出的实际线程数
4. 点「开始下载」→ 进度卡片出现，实时显示百分比、速度、剩余时间与分块状态
5. 完成后可点「打开文件夹」直达文件

### 线程档位：按本机核心数换算，不写死数字（v0.5.1 改）

一开始做成了固定档位（1 / 2 / 4 / 8 / 16），但这在换电脑时会出问题：
同一份程序在 4 核机器上开 8 线程是**过载**（反而更慢），在 32 核机器上开 8 线程又是**浪费**。
现在改成按本机**逻辑处理器（硬件线程）数**换算的三档：

| 档位 | 换算 | 本机（8 核 12 线程）实际值 |
| --- | --- | --- |
| 低 | 1/4 线程数 | 3 线程 |
| 中（默认） | 1/2 线程数 | 6 线程 |
| 高 | 全部线程数 | 12 线程 |

> **档位按"线程数"而不是"核心数"换算**，因为高档的定义就是"调用所有线程"，
> 而且下载是 IO 密集型——超线程出来的那部分并发同样能提高吞吐。

#### ⚠️ 「核心数」和「线程数」是两个数，界面上必须都写出来（v0.5.2 修）

v0.5.1 的提示文案写的是「本机 **12 核** · 中档 6 线程」，用户直接报"显示我有 12 核，
实际只有 8 核"。查下来 `os.cpu_count()` **本身没错**——它返回的是**逻辑处理器数**，
而这台 CPU 是 **8 物理核心 / 12 逻辑处理器**（4 个带超线程的 P 核 + 4 个 E 核，
典型如 i5-12450H）：

```
GetLogicalProcessorInformationEx(RelationProcessorCore) 的 8 条记录：
  off=  0  flags=1  掩码 2 位   ← P 核（含超线程兄弟）
  off= 48  flags=1  掩码 2 位
  off= 96  flags=1  掩码 2 位
  off=144  flags=1  掩码 2 位
  off=192  flags=0  掩码 1 位   ← E 核（单线程）
  off=240  flags=0  掩码 1 位
  off=288  flags=0  掩码 1 位
  off=336  flags=0  掩码 1 位
→ 记录条数 8 = 物理核心数；掩码位数之和 12 = 逻辑处理器数
```

真正的 bug 是**用词**：把逻辑处理器数写成了"核"，于是和首页 CPU 面板的
「8 核 12 线程」自相矛盾，用户合理地认为程序认错了 CPU。

现在两者都取、都显示：**「本机 8 核 12 线程 · 中档 6 线程」**，
这样"中档 6 = 12/2"也一眼能对上。

物理核心数用 ctypes 直调 `GetLogicalProcessorInformationEx(RelationProcessorCore)`
（毫秒级、不起子进程、不联网），两个实现要点：

- **必须用 `RelationProcessorCore(0)`**，不能用 `RelationAll(0xFFFF)`——
  后者会把缓存 / NUMA 节点等记录也混进来，条数就不是核心数了。
- **步长要用头里的 `Size` 字段**，不要自己算结构体大小：`PROCESSOR_RELATIONSHIP`
  有对齐填充，实际大小 40 字节、外层结构 48 字节，手算会错位。
  （顺带一提，`PROCESSOR_RELATIONSHIP.Flags` 的第 0 位就是 `LTP_PC_SMT`，
  可以用它直接判断该核心是否开了超线程，不必数掩码。）

拿不到核心数时（非 Windows / API 失败）不写"0 核"，退化成只显示线程数。

#### v0.5.3：收归 `sysinfo.py` 唯一数据源（换电脑也不会分叉）

v0.5.2 只是把下载页的数字改对了，但**首页和下载页仍然是各读各的源**：

| 页面 | 原数据源 |
| --- | --- |
| 首页 CPU 面板 | WMI `Win32_Processor.NumberOfCores / NumberOfLogicalProcessors`（走 PowerShell） |
| 下载页档位提示 | `os.cpu_count()` + `GetLogicalProcessorInformationEx`（ctypes） |

两个源大部分时候一致，但**在别的机器上会分叉**，风险有两处：

1. **多路（双路）机器**：WMI 会为**每个物理插槽**返回一条 `Win32_Processor`，
   而 `hardware.py` 原本写的是 `cpu = cpus[0]`——只取第 1 颗。
   双路机上首页会写「16 核 32 线程」、下载页写「32 核 64 线程」，又变成用户报的那个现象。
   现在改为**按插槽求和**，并加了单元测试（伪造一份双路载荷断言 32 核 / 64 线程）。
2. **WMI 本身可能拿不到值**（`Win32_Processor` 查询失败 / 仓库损坏 / 被策略拦），
   首页会显示 `--` 而下载页正常，同样显得像 bug。

因此新增 `sysinfo.py`，`cpu_cores()` / `cpu_threads()` / `describe_cpu()` 集中实现，
**首页与下载页都从这里取**（`downloader.py` 直接 re-export，两边是同一个函数对象）。
首页的 WMI 值降级为兜底：sysinfo 取不到时才用，且多路求和。

> 这条是通用原则：**同一个机器事实在多个页面出现时，必须同一数据源 + 同一套措辞**，
> 并加一个能同时断言两个页面的测试项。否则两处会各自漂移，
> 最后以"程序认错了硬件"的形式被报成 bug。
> 对应测试见 UI 测试第 [12] 段——它故意喂一份"谎报 4 核 8 线程"的假 WMI 载荷，
> 断言首页仍然显示 8 核 12 线程。

#### 换电脑的其它检查项

| 场景 | 处理 |
| --- | --- |
| 单核机器 | 三档都是 1 线程（下限保护，有测试） |
| 128 线程机器 | 高/中档被 `MAX_THREADS = 32` 截断（有测试） |
| 非 Windows / API 失败 | `cpu_cores()` 返回 0 → 只显示线程数，不写"0 核"（有测试） |
| 双路机器 | WMI 回退路径按插槽求和（有测试） |
| 不同分辨率 / 窗口尺寸 | 780×540（最小）~ 1920×1080 共 5 档 × 双主题 × 4 个页面，逐标签断言 `width ≥ sizeHint`，**零裁切** |

其它几个刻意的选择：

- 用**整除**而不是四舍五入：8 线程正好得到 2 / 4 / 8，口径最好解释。
- 下限 1（单核机器三档都是 1），上限 `MAX_THREADS = 32`（128 线程机器的高/中档都会被截断）。
- `os.cpu_count()` 返回 0 / None / 抛异常时保守按 4 线程处理。
- 引擎侧 `DownloadTask` 的默认值改成 `None` → 自动取中档，这样不传参也不会退回写死的 8。
- **UI 必须把换算结果显式写出来**，否则用户看着"中"根本不知道会开几个线程。

### 下载前先探测：为什么不能只看 URL 猜文件名

很多下载链接形如 `https://site.com/download?id=123`，光看 URL 只能得到 `download`。
所以点「开始下载」后先**后台探测一次**（`Range: bytes=0-0`），
一次请求同时拿到三件事：

| 探测项 | 用途 |
| --- | --- |
| `Content-Range` 里的总大小 | 算百分比与剩余时间 |
| 是否返回 **206** | 决定能不能分块并发 |
| `Content-Disposition` 的文件名 | 拿到服务器给的真实文件名（支持 `filename*=UTF-8''`） |

探测完自动接着下载，只需要点一次按钮。用户手动改过文件名就不再被服务器名覆盖。

### 分块可视化

进度条下方每个小方块对应一个下载分块，内部按进度从左填充。
一眼能看出**是不是所有线程都在推进**，以及哪个块拖了后腿——
比只有一个总进度条信息量大得多，也和极简色块的视觉语言一致。

### 关键实现细节

- **先预分配再并发写**：`f.truncate(total)` 把文件撑到最终大小，
  之后每个 worker 用**独立文件句柄** `seek` 到自己的区间写入。
  `seek` 是 per-fd 的，所以并发写同一文件的不同区域是安全的。
- **必须发 `Accept-Encoding: identity`**：否则服务器压缩后 `Content-Length`
  与解压后的大小不一致，分块偏移会全部错位——这是多线程下载最隐蔽的一类 bug。
- **按需降级**：服务器不支持分块（不返回 206）时不硬撑，自动转单线程流式写，
  此时只显示已下载量、不显示百分比。
- **`.part` 两段式落盘**：下载中文件叫 `xxx.part`，全部完成且**校验大小一致**后才
  `os.replace` 成正式名，避免半成品被误当完整文件。
- **同名不覆盖**：目标已存在时自动改成 `xxx (1).zip`，绝不静默覆盖用户的文件。
- **取消/失败先清盘再落状态**：顺序反过来的话，状态一变「已取消」UI 就刷新了，
  但此时 `.part` 还没删掉（删除带重试等待），表现为"取消了文件还在"，
  紧接着往同一路径再下一次还会撞车。
- **进度用 200ms 定时器轮询快照**，而不是让 worker 发高频信号——
  高速下载时后者会把主线程事件循环冲垮。
- **按钮与说明行随阶段走**：`_set_busy(True)` 写的是**探测阶段**的话术（"获取信息…"），
  任务真正跑起来后必须显式换成"下载中…"，说明行同理。
  这个 bug 是靠截图才发现的——当时 52 项逻辑测试全绿，界面上却全程写着
  "正在向服务器获取文件信息…"，因为 `_on_probed` 起来任务后没人去改这两处文案。

### v0.5.1 修复：浅色模式下右键菜单是黑的

**现象**：浅色模式右键点下载链接输入框，弹出的标准菜单**完全看不到字**。

**根因**在全局 QSS 的一条通配规则：

```css
QWidget {
    color: $text;
    background: transparent;   /* ← 祸根 */
    font-size: 13px;
}
```

这条规则**也会作用到 `QMenu`**。QMenu 是原生弹窗窗口，"透明背景"意味着它自身的底
根本不被绘制 → 漏出窗口默认的**黑底**；而文字颜色又老老实实跟着主题走。
于是：

| 主题 | 底色 | 文字 | 结果 |
| --- | --- | --- | --- |
| 浅色 | 黑（漏出来的） | `#14161a` 近黑 | **完全看不见** |
| 深色 | 黑 | `#f2f4f8` 浅色 | 勉强能读，所以一直没被发现 |

**修法**：给 `QMenu` / `QMenu::item` / `::separator` 补一套实心样式
（底 `card_top`、边 `border_strong`、选中态 `accent`）。
注意**条目要写在 `QMenu::item` 上**——只给 `QMenu` 设 `background` 的话，
菜单项本身仍是系统默认的白底。

**验证方式**（不能只看截图）：`QMenu` 的 `palette()` 才是屏幕上真正用的颜色，
断言"底色亮度 > 12 且与文字亮度差 ≥ 80"，两主题各一遍。

### v0.5.1 附带：右键菜单中文化

修完配色才发现这个菜单是**英文的**（Undo / Redo / Cut / Copy / Paste /
Delete / Select All）——`QLineEdit` 的标准右键菜单用的是 Qt 内置串，

- 翻译对象**必须留引用**（存进模块级 list），否则会被 GC 掉、翻译当场失效；
- 优先从 `resource_path("resources/qtbase_zh_CN.qm")` 读，
  找不到再退到 `QLibraryInfo.path(QLibraryInfo.TranslationsPath)`。

修完菜单项变成「撤消(U) / 重做(R) / 剪切(T) / 复制(C) / 粘贴(P) / 删除 / 全选」。
（注意 Qt 用的是"撤**消**"而非"撤**销**"，写断言时别写错字。）

## 系统驻留与启动（v0.6 新增）

三个功能各自独立，但都在处理"进程的一生"：怎么活下来、只活一个、什么时候自动活。

### 一、系统托盘驻留

托盘图标**常驻**（只要程序在跑就有），菜单三项：

| 菜单项 | 行为 |
| --- | --- |
| 显示主界面 | 显示窗口并提到前台 |
| 隐藏到托盘 | 收进通知区域 |
| 退出 Yuhub | 真正退出（走收尾流程） |

图标本身：单击 / 双击按"不可见就显示 → 可见但不在前台就提到前台 → 已在前台就收起来"三段式处理，
不必再翻菜单。首次收进托盘时会弹一次气泡说明——不弹的话用户会以为程序被关掉了。

两个必须记住的点：

1. **`app.setQuitOnLastWindowClosed(False)` 是前提**。托盘常驻模式下窗口只是
   `hide()`，但某些系统级关闭路径仍会触发 `lastWindowClosed`；留着默认行为，
   程序会在用户没要求的时候悄悄结束。所以退出完全走显式路径。
2. **托盘菜单要单独套一份样式**。主窗口的 QSS 是 `window.setStyleSheet(...)` 设的，
   只会级联到**该控件的后代**；托盘菜单是独立顶层弹窗、parent 不指向主窗口，
   拿不到那份样式表 → 退回系统默认外观，深色主题下白底刺眼、浅色主题下和界面完全不搭。
   所以 `ui/tray.py` 自己生成一份 QMenu 样式并挂在主题总线上跟随切换。

另外：托盘不可用时（精简版系统、部分远程会话）`close_to_tray` 会被**强制为假**，
一律退回真退出——否则窗口藏进一个不存在的托盘，用户就彻底失联了。

### 二、单实例：判定 + 唤醒

用 `QLocalServer` / `QLocalSocket`（Windows 下底层是命名管道），
一次调用同时解决"判定有没有实例"和"把已有实例叫到前台"两件事——
纯 Mutex 方案只能告诉你"有人了"，想再递一句话得另搭一套 IPC。

顺序上有三个坑，都是实测踩出来的：

**① 必须先 `connect` 探活，再 `listen`。**
直觉写法是"直接 listen，失败就说明已经有实例了"。这在正常退出下没问题，
但进程被强杀（任务管理器结束、崩溃）时命名管道可能没释放，新实例 listen 也失败 →
**再也起不来了**，用户只能重启电脑。正确顺序：

```
1. 先 connect 试连 → 连得上 = 对方真的活着，递激活消息后自己退出
2. 连不上才 removeServer 清残留 + listen
```

两个实例几乎同时启动时，可能双方都 connect 失败、都去 listen，第二个必然失败。
此时**再探活一次**：连得上就老实退出；连不上说明只是环境不允许命名管道
（极少数安全策略下会这样），那就**放弃单例保护、照常启动**——
宁可同时开两个窗口，也不要让用户怎么点都打不开。

**② 递消息必须有回执，客户端要等到 ack 再断开。**
第一版是"写完就 disconnect"，结果激活消息**静默丢失**：服务端可能还没读，
Windows 上它只看到"对端已关闭"、`readAll()` 返回空。
表现是"第二个实例确实退出了，但第一个实例的窗口根本不弹"。
现在服务端读到后回一个 `ack`，客户端等到才走。

**③ 服务端读数据时绝不能 `waitForReadyRead`。**
它是丢消息的真正元凶：`waitForReadyRead` 会开一个**嵌套事件循环**，
里层会把同一连接的 `disconnected` 先派发进来 → `_drop` 重入读取 →
此时 socket 已是 `UnconnectedState`、数据读不到，回到外层也无从补救。
所以服务端只做"有什么读什么"，数据到达交给 `readyRead` 信号驱动。

**④ 服务名要按登录用户区分，而且必须幂等。**
Windows 命名管道默认在当前登录会话内，不同用户同时登录（快速用户切换 / 远程桌面）时
同名管道会互相干扰且跨会话访问会被拒。所以服务名是 `{key}-{用户名}`。

幂等这条是补的：`is_another_running(server_name())` 这种写法太自然了，
但双重套娃会算出 `xxx-M1racle-M1racle`，于是"明明有实例却探测不到"，
**不报错、只是静默失联**。现在 `server_name()` 检测到已有后缀就不再拼。

### 三、开机自启

写 `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`（`autostart.py`，纯标准库）。

- 选注册表而不是"启动"文件夹放 `.lnk`：不用造 COM 快捷方式，开关就是增删一个值；
  而且用户能在**任务管理器 → 启动应用**里看到并手动禁用——Windows 读的就是这里。
- 用 `HKCU` 而非 `HKLM`：只影响当前用户，不需要管理员权限
  （要管理员的方案是没法"点一下就开"的）。

生成的命令行按运行形态分两种：

| 形态 | 命令 |
| --- | --- |
| 打包后 | `"C:\...\Yuhub.exe" --minimized` |
| 源码运行 | `"...\pythonw.exe" "C:\...\main.py" --minimized` |

源码运行必须用 `pythonw.exe`（同目录下，`sys.executable` 换成它才不开黑框），
并且 `main.py` 要写**绝对路径**——开机时工作目录是 `system32`，相对路径必挂。

**⚠️ 路径必须整段加引号**：程序若装在 `C:\Program Files\...` 这类含空格的目录，
不带引号会被拆成多个参数，开机时**静默启动失败**——不报错、不留痕迹，
用户只会觉得"这个自启时灵时不灵"。这是这类功能最常见的坑。

`--minimized` 让程序开机后**安静地驻留托盘**、不弹大窗口。这一条同时带来一个额外好处：
窗口从没 `show()` 过，`showEvent` 就不会触发，首页的硬件采集自然也跳过——
等用户真去看首页时再扫，不浪费开机那几秒。

设置页的开关还有两处细节：

- **写失败要把开关拨回去**。否则界面显示"已开启"、注册表里什么都没有，
  用户下次开机发现根本没启动，却完全不知道是这里失败了。
- **路径漂移检测**。程序被移动/改名后，注册表还指着老路径，自启会静默失效。
  所以开启状态下会比对注册表里的程序路径与当前程序，不一致就明确提示
  "建议关闭再重新开启以更新路径"。

### 关闭窗口的两条去向

| 条件 | 行为 |
| --- | --- |
| `close_to_tray` 为真（默认）且托盘可用 | 拦下关闭事件、只 `hide()`，进程留在托盘 |
| 关掉了开关 / 托盘不可用 / 从托盘菜单点退出 | 走收尾（停后台线程 + 撤托盘图标）后 `app.quit()` |

偏好存成字符串 `"true"` / `"false"`，读的时候显式判断：

```python
# 不用 value(key, default, type=bool)：
# Windows 原生格式存进去是字符串，取回来再转 bool 时 bool("false") 是 True
# →「关掉后重启又自己打开了」
raw = settings.value(key, None)
return str(raw).strip().lower() in ("1", "true", "yes", "on")
```

## 异地联机（v0.9 恢复，内嵌 EasyTier「跨网房间」）

> v0.9 起**只保留异地联机（跨网房间）这一种方案**；局域网直连（UPnP / 地址交换打洞）
> 已按需求移除。下文保留历史记录供参考。

**目标**：让两台不在同一局域网的电脑玩"局域网联机"游戏（Minecraft Java 等），
像 Radmin LAN / Hamachi 那样，但**无需自建服务器、无需公网 IP、无需路由器设置**。
内嵌 EasyTier（Apache 2.0 开源）创建一块二层虚拟网卡，房主和成员各填同一组
**房间码 + 密码**，即可进入同一个虚拟局域网，游戏里的「局域网」列表直接互相看到。

### 原理：EasyTier 虚拟网卡（P2P 打洞 + 社区节点中继兜底）

正统做法是 TUN/TAP 虚拟网卡 + 中继服务器。单文件 exe 分发驱动不现实，所以换了条路：

```
房主的游戏「对局域网开放」
   └─> 往 224.0.2.60:4445 组播 / 255.255.255.255:4445 广播
       「我在 192.168.1.5:52341」          ← 联机的全部线索

房主侧（Yuhub）                          成员侧（Yuhub）
  桥绑<每张网卡IP>:4445 抓到宣告          收到隧道来的宣告
  解析出游戏端口 52341        ──TCP隧道──>  把 192.168.1.5:52341 改写成
  把端口通告给所有成员                      127.0.0.2:52341（本机代理口）
                                          并按游戏原格式投递一条宣告
                                          → 游戏大厅直接出现房间

成员点进房间 → 连 127.0.0.2:52341
   └─> 代理口接住 ──TCP隧道──> 房主连 192.168.1.5:52341 → 游戏
```

成员的游戏完全不知道中间有中转。

### 关键结论全部实测得出（Windows 11）

这些是设计的地基，**每一条都是跑出来的，不是查文档猜的**：

| 实验 | 结果 | 结论 |
| --- | --- | --- |
| 两个 UDP socket 都绑 `0.0.0.0:P`（后者带 REUSEADDR） | 后者 bind 失败（errno 13） | 不能和游戏抢通配绑定 |
| 两个都带 REUSEADDR 绑同一 UDP 端口 | 都能 bind，但**只有先绑的收到包** | 共享端口抓包不可靠 |
| TCP 两个都带 REUSEADDR listen 同端口（都绑 `0.0.0.0`） | **都能 listen 成功**，但连接 **100% 全部给先绑的那个**，后绑者一个都收不到 | 代理口**绝不能**设 REUSEADDR（否则连接全被游戏抢走） |
| 游戏 `0.0.0.0:P`，桥绑 `<网卡IP>:P`+REUSEADDR | **共存，广播两边都收到** | 桥绑具体网卡地址 ✅ |
| 游戏 `0.0.0.0:P`，代理绑 `127.0.0.1:P`（TCP） | 共存，回环连接**优先给更具体的绑定** | 但见下条 |
| 代理从 `127.0.0.1` 发包给游戏 | 游戏收到，代理不截留 | 投递路径干净 ✅ |
| 代理改绑 `127.0.0.2:P` | 与游戏彻底隔离：发往 `.0.1` 的给游戏、发往 `.0.2` 的给代理 | **代理口统一用 127.0.0.2** ✅ |

`127.0.0.2` 属于 `127.0.0.0/8` 整段回环，Windows 天然可用——它是"另一个回环地址"，
和游戏占用的 `127.0.0.1` 互不干扰，还顺便解决了"房主游戏恰好监听同号端口"的冲突。

### 三个必踩的实现坑（测试抓出来的真 bug）

1. **流帧忘了带 stream id**：`T_STREAM_OPEN` / `T_STREAM_ACK` 走默认的控制通道 id=0，
   对端按 sid 查不到流 → 双方能连上但**一个字节都传不动**。所有流消息必须把 sid 填进帧头。
2. **被动方的流没置 ready**：房主侧建好流后 `ready` 仍是 False，
   游戏返回的数据全被当成"等待确认"塞进缓冲——连接正常、游戏收到了包、但永远没有回包。
3. **拒绝消息发不出去**：`peer.close()` 会连队列里还没发的 WELCOME 一起丢，
   对方只看到"连接被断开"，提示变成含糊的"房主没有回应"。
   必须 `close_after_flush()`：把队列发完再关。

### 端口与地址约定

| 名称 | 默认值 | 说明 |
| --- | --- | --- |
| 发现端口 | `4445/udp` | 游戏广播「我开房了」的端口（Minecraft），桥监听它 |
| 控制端口 | `42545/tcp` | Yuhub 房间的主隧道端口，队友连这个 |
| 游戏端口 | 自动识别 | 从游戏的宣告里解析（Minecraft 开房后聊天栏也会显示） |
| 代理口 | `127.0.0.2:<游戏端口>` | 本机游戏该连的地址；端口被占会自动改号并同步改写宣告 |
| UPnP | 房主自动尝试 | 映射控制端口到公网；失败则异地联机需手动在路由器转发 |

#### v0.10.2 修复：创建房间后一直显示「正在启动…」

症状：点「创建跨网房间」后按钮永久停在"正在启动…"，房间其实已经建好。
一次排查揪出**三个叠加的 bug**，任何一个单独存在都会造成这个现象：

**① 按钮文案在成功路径上没复位（用户直接看到的那个）。**
`_set_running(flag)` 里复位按钮文案的代码被包在 `if not flag:` 分支里 —— 也就是
**只有"停止"时才会把文案改回去**。启动成功走的是 `_set_running(True)`，于是按钮
永远停在"正在启动…"。修法：文案复位移到条件外，成功/失败都无条件恢复。

**② watchdog 可执行文件在源码态指向了 `python.exe`。**
`_yuhub_exe_path()` 原来直接返回 `sys.executable`。源码运行时那是 `python.exe`，
而 `ShellExecuteW("runas", "python.exe", "--watchdog <b64>")` 会让 Python 把
`--watchdog` 当成**脚本文件名**去找，找不到立刻退出；`core_running()` 在宽限期后
仍为假 → 报出误导性的"EasyTier 进程意外退出（密码含特殊字符或节点不可达？）"。
而且 `python.exe` 是控制台程序，runas 启动它还会闪黑窗——正是 watchdog 方案
当初要消灭的现象。修法：打包态用 `sys.executable`，源码态去项目根找构建好的
`Yuhub.exe`；并新增 `watchdog_capable()` 前置校验，不可用时直接给出可操作的
提示（"先构建或改用打包后的 exe"），而不是让用户看到假错误。

**③ "进程意外退出"的 3 秒宽限期从错误的起点计时。**
原判据是"距**发起提权**超过 3 秒且 core 没在跑 → 判定意外退出"。但用户看到 UAC
弹窗后可能去接杯水，这段等待里 core 本来就还没起来 —— 只要点"是"慢了 3 秒就会被
误判。修法：改成"**曾经出现过** core 之后才开始计时"，并在日志里明确写出
"easytier-core 已拉起，正在等待虚拟网卡就绪…"。超时提示也按"根本没起来"和
"起来了但网卡没就绪"两种成因分别给建议。

另外把 `parent_name` 从 `sys.executable` 的 basename 改为用
`QueryFullProcessImageNameW` 读**真实映像名**，避免 watchdog 的防 PID 复用校验
对不上而误判父进程已死。

**回归测试**：新增 `lan_selftest.py` + `Yuhub.exe --lan-selftest <out.json>`，
在 exe 内部跑真实启动全流程并断言 15 项（含上面三条的专项回归：
"成功后启动按钮不再是「正在启动…」"、"watchdog 指向 Yuhub.exe 而非 python.exe"、
"启动结束后 busy 标记已复位"）。源码态与打包态均 **15/15 通过**，打包态实测
房间 2.9 秒建好、虚拟 IP `10.126.126.1`、停止后网卡正确释放。

- **UPnP 方案（v0.7.1 引入）已于 v0.8.1 移除**：跨网统一走上面的跨网房间模式，
  `upnp.py` 保留但不再被调用。
- **安全**：房间码 + 密码双重校验。密码**不落盘、不通过明文传输**（握手用
  挑战-响应：房主下发随机 nonce，成员回算不可逆哈希，房主恒时比较）；
  房主停房后密码即从内存清除。抓包只能看到 nonce 和哈希，无法还原密码、也无法重放。
  跨网房间同理：EasyTier 的 network-secret 不经过任何第三方，仅用于组网握手。
- **游戏兼容**：靠"局域网广播发现 + TCP 连接"的游戏（Minecraft Java 等）开箱即用；
  纯 UDP 游戏或不用广播发现的游戏，可手动填游戏端口走代理口直连。
- 首次运行 Windows 防火墙会弹窗，必须允许，否则隧道建不起来。

## 软件卸载（v0.10 新增）

对标 [Geek Uninstaller](https://geekuninstaller.com/)：Windows 自带的"程序和功能"只负责
**调用**卸载程序，不负责善后。大量软件的卸载器只删掉安装日志里记录的文件，
运行时产生的 `%APPDATA%` / `%ProgramData%` 数据、注册表里扩散的厂商键全都留着。
本页在卸载器跑完之后**独立扫描**这两处，把残留摆到用户面前由他确认清理。

### 使用流程

1. **进入页面自动扫描一次**（v0.10.1 起）：不需要点任何按钮就能看到完整列表
2. 搜索 / 按名称·体积·日期·发布者排序；需要时打开「显示系统组件与运行库」开关
3. 点选一个程序 → **卸载选中程序** → 确认弹窗 → 软件自带卸载器开始工作
4. 卸载器结束后自动深度扫描，列出残留的文件目录与注册表项（默认全选）
5. 取消勾选的项会保留 → 点「清理选中残留」→ 二次确认 → 清理并复核
6. **卸载流程结束后自动重扫列表**（v0.10.1 起）：条目立刻消失，不用手动点「重新扫描」

卸载器已损坏、或程序文件被手工删掉时，用 **强制清除残留** 跳过第 3 步直接扫。

### 残留列表的关闭入口（v0.10.3 修复）

残留卡片有三个操作：全选 / 全不选 / 清理选中残留 —— **但曾经没有"关闭"**。
点开「强制清除残留」后卡片就一直挂在页面上，用户找不到取消的办法，
只能靠"卸载下一个程序"才会被内部清场逻辑顶掉。这是纯粹的 UI 死角。

修法：卡片加 **「关闭」** 按钮（`_dismiss_leftovers`），并把状态栏写成
**"已收起残留列表（N 项未处理）"** —— 这句提示很重要，否则用户会以为
残留已经被清理或忽略掉了。点「关闭」纯粹是收 UI，**不删任何东西**。

> 注意区分两个方法：`_clear_leftovers()` 是内部状态重置（开始新一轮卸载/扫描
> 前清场，不写状态栏）；`_dismiss_leftovers()` 是用户主动收起（要写状态栏、
> 还要刷新选中态）。混用会导致"状态栏留着过期的残留结论"。

另外确认框的取消路径也补了回归测试：点「取消」/「✕」/按 Esc **都不能触发清理**，
且取消后残留卡片必须保留（用户可能只是想先看看再决定）。

### 删除权限与只读属性（v0.10.4 修复）

现象：**AppData 里的文件删不掉**，点清理转一圈回来文件还在原地。

这不是一个 bug，是**三个问题叠在一起**：

#### ① `_needs_admin` 的判定范围太窄

旧实现只认三个前缀：

```python
for pre in ("c:\\program files", "c:\\programdata",
            "c:\\windows", "c:\\users\\all users"):
```

AppData 的路径是 `C:\Users\<名>\AppData\Local\...`，**一个都不匹配**，于是全部
按普通权限删。但 AppData 里恰恰混着大量"安装程序创建、ACL 只给了 SYSTEM 或
管理员"的目录——最典型的是 `AppData\Local\Packages\` 下的 UWP 包目录，
普通权限必失败。

现在改成三层判定：

1. 注册表：HKLM / HKCR 提权，HKCU 不提权（属于当前用户）。
2. 系统前缀 + `AppData\Local\Packages\`（UWP 特殊 ACL）。
3. **其余路径实测**：在目标位置试建一个临时文件，建不了就判定需要提权。

第 3 层是启发式，可能漏判，所以还有下一层兜底。

#### ② 只读属性连管理员都删不掉

这是个常见误解：**提权 ≠ 能删只读文件**。Windows 的只读是个硬属性，
`DeleteFile` 遇到它直接返回 `ERROR_ACCESS_DENIED`，管理员进程一样失败。

旧 `_delete_dir` 没有任何摘属性的动作，所以"只读残留"无论提权多少次都清不掉，
用户看到的就是"权限不够"。

新增 `_clear_readonly()` / `_dir_tree_clear_readonly()`，在删除前把
READONLY / HIDDEN / SYSTEM 三个属性统一摘掉，然后**重试一次**（刚被卸载程序
释放的句柄有延迟，立刻删会失败）。

#### ③ `MoveFileEx` 把权限失败误报成成功 ← 最隐蔽的一个

`_delete_dir` 在 `os.remove` 失败时会调 `_move_file_delayed()`（标记重启后删除）。
问题在于：**它几乎对任何路径都返回 True**，包括那些因为权限不足而根本不该被
登记的路径。于是 `failed` 永远是 0，走进这条误导性分支：

```python
elif failed == 0:
    # 目录还在但没报失败：多半是被策略层（如回收站重定向）拦下
    res.messages.append(f"未能删除（可能被安全策略拦截）{it.path}")
```

"可能被安全策略拦截"是个死胡同——它既不说清原因，也**不会触发任何提权动作**。

修复后：

- `_delete_dir` 返回 **4 元组** `(gone, size, failed, why)`，`why` 带真实错误文本；
- 没删净的路径进入 `CleanResult.retryable`；
- UI 侧 `_run_clean_leftovers` 在普通权限批次的 `retryable` 非空时，
  **自动把这些项并入提权批次重试**——这是最后一道保险：即便 ① 的启发式漏判，
  失败也会被抓回来提权。

#### 附带修掉的隐患：`sys_executable()` 指向 python.exe

提权子进程靠 `--uninstall-elevated` 开关识别自己。源码模式下
`sys.executable` 是 `python.exe`，把它 runas 起来参数会被当成脚本名
（`can't open file '--uninstall-elevated'`），还会闪一个黑窗口。
现在和 `etier.py` 用同一套策略：冻结时用自己，否则找构建好的 `Yuhub.exe`，
都找不到就通过 `elevation_capable()` 返回明确原因，而不是让用户盯着
莫名的 UAC 弹窗。提权结果回传也改成原子写（先写 `.tmp` 再 `os.replace`）。

> 自检里新增 6 项断言覆盖上述路径（含真实文件系统上的只读删除实验），
> 卸载页自检从 15 项扩到 **21 项**。对照实验：同样的只读目录，
> 旧实现 `gone=False failed=1`，新实现 `gone=True failed=0`。

### 两处自动扫描的时序设计

**进页扫描**：`on_shown()` 里挂 `QTimer.singleShot(120, start_scan)` —— 延迟 120ms 是
为了让页面先渲染出来，否则进度条会跟页面动画抢帧、看起来像卡了一下。
`_scanned_once` 标记保证来回切页面只扫第一次，不打断用户已勾选的状态。

**卸载后重扫**：`_auto_rescan_after_uninstall()` 延迟 260ms 再触发，意义是
**让残留卡片先渲染出来**——否则刚显示的残留结果会被"扫描中"的进度条盖住闪一下。
两个容易踩的点：

- **成功和失败分支都要重扫。** 卸载失败不代表列表没变——卸载器可能已经
  删了文件但没删注册表项（或反过来）。只在成功分支重扫会留下幽灵条目。
- **不能直接丢弃正在跑的扫描。** 如果上一次扫描还没结束（用户连点两次卸载），
  直接新建 `AppScanner` 会让结果乱序。现在的做法是在 `_silent_rescan` 里
  最多重试 6 次（约 1.8 秒），等上一次落地再发起。

重扫走 `quiet=True`：**不覆盖状态栏里刚写好的卸载结论**（"卸载完成，未发现残留"），
也不弹 toast——否则用户会连着看到两个提示，很吵。

### 打包后自检：`--uninstall-selftest`

上面这两条时序逻辑**在打包后没法用外部脚本可靠驱动**（150% 缩放下点击落点不准、
无边框+半透明窗口 `PrintWindow` 渲染空白、`PostMessage` 用客户区坐标而截图是屏幕坐标）。
所以给 exe 加了一个自检开关，让它**在内部**把真实 `UninstallPage` 跑一遍：

```bash
Yuhub.exe --uninstall-selftest <结果.json路径>
```

跑的是真正的页面对象（不是简化复刻），断言 15 项：
进页自动扫描 / 扫描完成 / 状态栏写入 / 图标渲染 / 卸载完自动重扫 /
静默重扫真的执行 / 不覆盖卸载结论 / 重扫后列表有效 / 失败分支也重扫 /
**残留卡片有「关闭」入口 / 点关闭真的收起 / 收起后状态栏提示残留未处理 /
确认框取消不触发清理 / 取消后残留卡片保留 / 确认才真正清理**。
同时回传运行时能力快照（`QFileIconProvider` 是否可用、`_ps_exe` 解析结果、
枚举源数量），用来排查"打包后某能力丢失"。

### 默认过滤掉什么（以及为什么）

| 来源 | 说明 |
|---|---|
| `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall` | 64 位程序 |
| `HKLM\SOFTWARE\WOW6432Node\...\Uninstall` | 32 位程序 |
| `HKCU\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall` | 当前用户安装的程序 |
| `HKCU\SOFTWARE\WOW6432Node\...\Uninstall` | 32 位 **按用户**安装的程序 |
| `Get-AppxPackage`（PowerShell） | 应用商店 / UWP 应用 |

后两个是容易漏的：**32 位按用户安装**的程序只登记在 `HKCU\WOW6432Node` 下，
少了这一处，本机装的那些"绿色软件 + 安装器"就全看不见了。

UWP 的注册表路径（`AppModel\Repository\Packages`）在不同 Windows 版本上结构不一致，
**实测本机只返回 1 个子键、完全不可用**，所以改用官方 cmdlet `Get-AppxPackage`。

### 换台电脑也能用：四处必须修的可移植性坑

「在我机器上能跑」和「在别人机器上能跑」是两回事。逐项排查后修掉四处：

**坑一：PowerShell 输出编码（最隐蔽，会让功能直接失效）。**
`subprocess.run(..., text=True)` 按**本机首选编码**解码，但 PowerShell 输出的是
**控制台 OEM 代码页**——中文 Windows 是 CP936，英文是 CP437。
两者不一致时 `UnicodeDecodeError` 在读取线程里抛出，`p.stdout` 变成 `None`，
**函数静默返回空列表，看起来像"没有装任何软件"**。
修法三步走：脚本前缀强制 `[Console]::OutputEncoding=UTF8` → 按 bytes 收结果 →
自己 `decode("utf-8", "replace")` → 若替换字符 ≥ 2 个再用 `gbk` 重试取更优解。

**坑二：`powershell` 不在 PATH 上。** 直接用裸名依赖 PATH，被裁过的系统或
32 位进程（WOW64）下会找不到。改为 `shutil.which` → `System32\WindowsPowerShell\v1.0`
→ `Sysnative`（32 位 Python 访问 64 位系统目录的唯一正确入口）。

**坑三：环境变量缺失。** 别人的注册表里可能写着 `%ProgramFiles(x86)%\Foo`，
但 32 位进程里**这个变量不存在**（`ProgramFiles` 本身就指向 x86 目录）。
`os.path.expandvars` 对这种未知变量原样返回，路径就废了。改成逐个手动兜底，
最后再用正则检查还有没有残留 `%VAR%`——有就返回空串而不是返回一个错路径。

**坑四：HKCU32 枚举源缺失**（见上一节表格）。

### 列表里显示每个软件的真实图标

**核心结论：`QIcon("某.exe")` 返回空。** Qt 的 `qico` 插件只读 `.ico` **文件**，
不会去解析 PE 文件里内嵌的图标资源。正确做法是用 **`QFileIconProvider`**
（底层走 Windows Shell 的 `SHGetFileInfo`），exe / dll / 任意文件都能取到，
实测有效 exe 返回 72×72。

图标来源按优先级回落（`_icon_source`）：

1. `DisplayIcon` —— 注册表里最准的一条，注意末尾可能带 `,索引`（要**从右往左**解析，
   因为路径本身可能含逗号）
2. UWP 的 `AppxManifest.xml` 里的 `<Square44x44Logo>` / `<Logo>` 等，
   相对 `InstallLocation` 解析，并处理 `*.scale-200.png` 这类变体
3. `InstallLocation` 下找主程序
4. 有界递归搜索（见下）
5. `UninstallString` 里的那个 exe

**为什么要费力找"主程序"而不是随便挑个 exe**：安装目录里躺着大量
`unins000.exe`、`vcredist_x64.exe`、`DXSETUP.exe`，它们的图标是卸载器/运行库的，
拿来当软件图标会**张冠李戴**（Epic Games Launcher 一开始就显示成了 DXSETUP 的图标）。
现在的策略是**打分 + 降级**：

- 噪音词表（`unins` / `uninstall` / `setup` / `update` / `vcredist` / `dxsetup`
  / `redist` / `dotnetfx` / `aria2`…）直接排除
- 低优先目录（`redist` / `directx` / `runtime` / `docs` / `locale`…）不进入搜索
- 目录名按 `win64|x64|bin` → `launcher|client|app` → `win32|x86` → 其他 排序
- 深度上限 5 层、每层最多 12 个子目录（Epic 那种 5 层嵌套实测 2ms 出结果）
- 最终仍找不到时**只按名称匹配**，不用"体积最大"兜底（体积最大往往就是运行时组件）

实测覆盖率（本机 46 个第三方程序）：**87%（40 个拿到真实图标）**。
剩下 6 个是**注册表里留下的陈旧条目**——Roblox / 剪映 / DF Launcher /
Epic Online Services 指向的文件早已被删，系统里根本没有图标可取，
此时回落成"首字母色块"，这是预期行为而不是 bug。

### 默认过滤掉什么（以及为什么）

本机 112 个注册表条目里，只有 75 个有 `DisplayName`、62 个有可执行的卸载命令。
剩下的是 Windows 留下的空壳（`AddressBook`、`IE40` 之类，没有名字也没有卸载命令）。
不加过滤地全列出来只会让用户困惑，所以默认隐藏：

- 无 `DisplayName` 或无任何卸载命令的条目
- `SystemComponent=1`（VC++ 运行库、NVIDIA 驱动组件等 24 项）
- 名称匹配系统组件模式（Edge、Edge WebView2、.NET、DirectX、Vulkan 等）
- `ReleaseType` / `ParentKeyName` 非空（属于某个父程序的更新包）

要看到它们，打开「显示系统组件与运行库」开关即可——对应 Geek 的"显示系统组件"。

### 卸载命令构造：两个必须区别对待的坑

**坑一：MSI 的 `/I` 是安装不是卸载。** 注册表里常见 `MsiExec.exe /I{GUID}`，
直接执行会变成"修复安装"。必须改写成 `/X {GUID} /qn /norestart`。

**坑二：不要凭空添加静默参数。** 只在软件**明确提供** `QuietUninstallString` 时才走
静默卸载；其余情况一律原样执行它自己的 `UninstallString`。
这里曾经犯过错——给只有 `UninstallString` 的程序硬塞 `/S`，把不认这个参数的卸载器
搞乱了（如"雷神加速器""iloader"）。

**坑三：引号。** `CommandLineToArgvW` 在这个场景拿不到正确结果，手写正则又会把引号
留在 token 里（`'"powershell"'` → 找不到可执行文件）。现在的实现自己按 Windows 规则
解析：引号分组、反斜杠转义，并对"路径含空格但没加引号"的情况做贪心回溯
（逐个空格位置试切，找到真实存在的文件为止）。

### 等待进程树结束，而不是主进程退出

很多卸载器会 fork 一个子进程干活、自己先退出。若主进程一退就开始扫残留，
会把正在被删除的文件误判成残留。所以卸载后要等整个进程树收尾，再多给 2 秒宽限。
提权路径下拿不到进程句柄，改为按 exe 名轮询 `tasklist`。

### 残留扫描的三条线索

| 线索 | 做法 | 准度 |
|---|---|---|
| A. 已知路径 | `InstallLocation` 直接圈定 | 最高 |
| B. 关联路径 | 从 `DisplayIcon` 反推程序目录 | 高 |
| C. 搜索发现 | 在 `%APPDATA%` / `%LOCALAPPDATA%` / `%ProgramData%` 下按名称匹配 | 需收紧 |
| D. 注册表 | 在 `HKLM` / `WOW6432Node` / `HKCU\SOFTWARE` 下按名称匹配（限深 2 层） | 需收紧 |

### C 和 D 的匹配规则是这套实现最关键的部分

**踩过的坑（真实误伤）**：最初用"关键词子串匹配"——把产品名切成词再逐个去目录名里找。
拿 Epic Games Launcher 一试，"Launcher" 这个词命中了 `WPFLauncher`、
`nrc_launcher`、`delta_force_launcher`、`MCLauncher`——**全是别的软件**。
18 项"残留"里只有 5 项真的属于 Epic。

现在的规则（`_app_keys` + `_appdir_matches`）：

1. 生成**指纹**而不是关键词：产品名拼接（`Epic Games` → `epicgames`）、
   安装目录末级名、图标路径目录名
2. 目录名去符号后 **== 指纹** 才匹配；或指纹长度 ≥ 6 时允许**包含**
3. 长度门槛 4：`steam`、`7zip`、`epic` 能过，`app`、`web`、`hub` 进不来
4. 通用词表大幅扩充（约 200 词），把 `launcher`、`client`、`manager`、
   `support`、`driver` 这类高危词全部拉黑

效果：Epic 的残留从 18 项（10 项误伤）降到 9 项，全部真实相关。
回归测试固定 9 个用例：`epicgameslauncher` ✓、`epic games` ✓、
`wpf launcher` ✗、`mclauncher` ✗、`delta_force_launcher` ✗、`steam` ✗。

### 安全设计（与清理页同一套原则）

- **扫描纯只读**：进页面只枚举，不做任何删除
- **删除前二次确认**：逐项列出路径与体积，明确写"不可撤销"
- **白名单校验**（`_is_safe_to_delete`）：拒绝 `C:\Windows`、`Program Files`、
  `ProgramData`、`C:\Users` 等**根本身**，以及任何盘符根目录、用户主目录本身。
  但允许其**子项**（`D:\Games`、`C:\ProgramData\VendorX` 都是正常安装位置）
- **被占用的文件**用 `MoveFileExW(..., MOVEFILE_DELAY_UNTIL_REBOOT)` 标记重启后删除
- **需要管理员权限的项**走 `Yuhub.exe --uninstall-elevated <base64-json>` 提权子进程
  （弹一次 UAC、无窗口静默执行、结果 JSON 回传），判定依据是路径前缀与 hive

### 一处容易漏掉的残留：卸载信息登记项

程序自己的卸载信息键在
`...\Microsoft\Windows\CurrentVersion\Uninstall\<子键>` 之下，
而常规注册表扫描为了安全会**跳过 `Microsoft` 子树**。
但这一项恰恰是卸载后必须清掉的（否则控制面板里永远留一个幽灵条目）。
所以单独用**精确 subkey**定位补一条，不做任何模糊匹配。

### 打包后验收（v0.10.1 冷冻包）

打包只是第一步，**模块是否真的进了包、打包后还能不能跑**要单独验：

1. **PYZ 模块校验**——`CArchiveReader` 的 TOC 顶层看不到纯 Python 模块（它们在被
   压缩的 `PYZ.pyz` 里，格式与 zip 不同）。正解是 `extract('PYZ.pyz')` 落盘后交给
   `ZlibArchiveReader`（注意 `extract()` 只接受 `name` 一个参数，返回 bytes，不落盘）。
   实测 160 个模块，`uninstaller` 与 `ui.pages.uninstall_page` 均在包内。
2. **界面启动截图**——标题 `v0.10.0`，侧栏 6 项；进入「软件卸载」页显示
   **47 个程序 · 已知体积合计 8.7 GB**，**每个程序带真实图标**（5EClient / 7-Zip /
   AntiCheatExpert / Apex Legends / Counter-Strike 2 / Epic Games Launcher…）。
3. **冻结代码路径实测**——`Yuhub.exe --uninstall-elevated <base64-json>` 返回 0，
   真实删除临时目录并回传 `{"freed": 8192, "removed": 1, "failed": 0}`，
   说明早返回分支、`import uninstaller`、`clean_leftovers` 全部可用。
4. **自动扫描自检**——`Yuhub.exe --uninstall-selftest <out.json>` 返回 0，
   **9 项断言全过**，`frozen: true`，`QFileIconProvider: ok 72x72`，
   `_ps_exe` 正确解析到 `System32\WindowsPowerShell\v1.0`，枚举源 4 处。

> **GUI 自动化注意**：本机 150% 缩放。外部脚本不做 DPI-aware 时
> `GetWindowRect` 返回逻辑坐标、点击却用物理坐标，会系统性错位；
> 先 `SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2)` 再取矩形。
> 沙箱内 `SendInput` 点不动应用，改用 `PostMessageW` 发鼠标消息；
> onefile 包会 fork 子进程，需按进程名而非 `Popen` 的 PID 找窗口。
>
> **还有一个更硬的限制**：`PostMessageW` 收发的是**客户区坐标**，而截图拿到的是
> **屏幕坐标**，两者在 150% 缩放下对不上，点"复选框"会落到"设置中心"去。
> 加上窗口是 `FramelessWindowHint + WA_TranslucentBackground`，
> `PrintWindow` 渲染出来是全白。所以涉及页面内部时序的验证**不要硬啃外部自动化**，
> 走 `--uninstall-selftest`（见上）在 exe 内部跑真实对象。
> 外部脚本只用来做"启动 + 截图"这种不需要精确落点的事，
> 且截图要用 `CopyFromScreen` 抓屏，不能用 `PrintWindow`。

### 已知限制

- 卸载向导本身会弹窗（软件自带的，无法也不需要绕过），需要用户自己点完
- 部分卸载器不支持任何静默参数，只能走向导
- 注册表扫描限深 2 层，很深的厂商键可能漏（宁可漏也不误删）
- 安装日期只有部分软件在注册表里提供，缺失时显示 `--`
