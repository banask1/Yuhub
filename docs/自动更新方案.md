# Yuhub 自动更新方案（设计稿）

> **状态：已实现**（v0.8beta）。代码见 `updater.py` + `ui/update_ui.py`，
> 自检见 `update_selftest.py`（`Yuhub.exe --update-selftest <out.json>`，28/28 通过）。
> 实现时发现并修掉了一个方案阶段没预料到的坑，见文末「实现补充」。
>
> 目标：单文件 `Yuhub.exe` 能自己检查新版本、下载、替换自己并重启。
> 三个已定决策：**GitHub Releases 托管** / **整体替换 exe** / **静默检查 + 手动触发**。

---

## 一、为什么"替换自己"是最难的

Windows 上**正在运行的 exe 无法被覆盖**（文件被映射为映像，占用句柄）。
所以自更新必须让**另一个进程**在旧进程退出后完成替换。

主流做法有三种，选哪种直接决定复杂度：

| 做法 | 思路 | 评价 |
| --- | --- | --- |
| A. bat / cmd 脚本 | 生成临时 `.bat`，等旧进程退出 → `copy` / `move` | 简单，但会闪黑框；本机是 GUI 子系统程序，用户对黑框敏感 |
| B. 独立 updater.exe | 单独打包一个小 exe 负责替换 | 最规范，但多一个构建产物要维护、还要处理它的自更新 |
| **C. 复用自身 exe（推荐）** | `Yuhub.exe --apply-update <base64-json>` 新起一个自己当"替换器" | **零新增产物**，且项目已有成熟的早返回模式可照搬 |

**选 C。** 理由：项目里 `--watchdog` / `--clean-elevated` / `--uninstall-elevated`
已经是同一套模式，`main()` 开头就是一堆早返回分支。加一个 `--apply-update`
几乎不引入新概念，而且 `--windowed` 打包的 exe 被 runas / subprocess 拉起时
**不会弹控制台窗口**——这是 bat 方案做不到的。

## 二、整体架构

```
┌─ 主进程 Yuhub.exe ──────────────────────────────────────┐
│                                                          │
│  ① 启动时静默检查（后台线程，不阻塞 UI）                  │
│     GET https://api.github.com/repos/<owner>/<repo>/     │
│         releases/latest                                  │
│     → 拿 tag_name(v0.12.0) / body / assets[]             │
│                                                          │
│  ② 版本比对  v0.12.0 > 0.11.1 ?                          │
│     有新版 → 只更新 UI 状态（设置页小红点 + 提示）         │
│                                                          │
│  ③ 用户点「检查更新」或「立即更新」                        │
│     → 下载 asset 到 %LOCALAPPDATA%\Yuhub\update\          │
│       下载复用 downloader.py（断点续传 + 进度回调）        │
│                                                          │
│  ④ 校验 sha256（可选但强烈建议，防下载损坏）               │
│                                                          │
│  ⑤ 把"当前的自己"拷到临时目录当替换器                         │
│     %TEMP%\Yuhub_upd_<pid>\Yuhub_updater.exe                 │
│     写更新请求 JSON → 拉起替换器 → 退出自己                   │
│     subprocess.Popen([updater, "--apply-update", b64])      │
│                                                          │
└──────────────────────────────────────────────────────────┘
                          ↓ 旧进程退出
┌─ 替换器（临时目录里的副本，--apply-update 模式）─────────────┐
│  ⑥ 等旧 PID 完全消失（WaitForSingleObject，超时则强杀）      │
│  ⑦ 两步改名：                                               │
│       Yuhub.exe      ->  Yuhub.exe.bak                      │
│       new.exe        ->  Yuhub.exe                          │
│     失败则回滚（把 .bak 改回来）                             │
│  ⑧ 启动新 Yuhub.exe（带 --updated-from，用于提示更新成功）    │
│     5 秒内秒退 → 判定新版有问题 → 自动回滚到 .bak 并启动旧版   │
│  ⑨ 自己退出（可选：清理 .bak 与自己的临时目录）               │
└──────────────────────────────────────────────────────────┘
```

**为什么要独立副本**：见第四节——替换器自己不能是它要替换的那个文件。

## 三、版本清单（放哪里、长什么样）

### 方案 A（推荐）：直接用 GitHub Releases API

不额外维护 `version.json`，靠 **Release 的 tag 当版本号**、**body 当更新说明**、
**assets 当下载地址**。

```
GET https://api.github.com/repos/<owner>/<repo>/releases/latest
```

```json
{
  "tag_name": "v0.12.0",
  "name": "Yuhub v0.12.0",
  "body": "## 更新内容\n- 修复下拉框样式\n- 设置页精简",
  "published_at": "2026-10-01T10:00:00Z",
  "assets": [
    { "name": "Yuhub.exe", "size": 59265602,
      "browser_download_url": "https://github.com/.../Yuhub.exe",
      "digest": "sha256:abc123..." }
  ]
}
```

优点：发布流程就是 `git tag v0.12.0 && gh release create`，零额外工作。
`digest` 字段 GitHub 官方已支持，可直接拿来校验。

### 方案 B：自建 `version.json`

```json
{
  "version": "0.12.0",
  "notes": "修复 ...",
  "url": "https://cdn.example.com/Yuhub-0.12.0.exe",
  "sha256": "abc123...",
  "min_supported": "0.9.0",
  "force": false
}
```

好处是能表达 `min_supported`（低于此版本必须更新）和 `force`（强制更新），
GitHub Releases 表达不了。**建议：先只做 A，需要时再叠加 B。**

## 四、替换手法：用「改名」而不是「覆盖」⚠️

这是本方案**最容易翻车的点**，已用真实 exe 实测（见下方实验记录）。

### 实测结论（Windows 11 / 本机）

对**正在运行**的 exe 文件：

| 操作 | 结果 |
| --- | --- |
| 改名 `os.rename` | ✅ **成功** |
| 覆盖写 `open(path,"r+b")` | ❌ `PermissionError [Errno 13]` |
| 整文件替换 `os.replace` | ❌ `WinError 5 拒绝访问` |

原理：Windows 把运行中的 exe 映射为**映像节**，**禁止改写文件内容**，
但**只改目录项（改名）是允许的**——内容没被动过。

### 由此得到的最佳替换法：两步改名

```
1. 旧 exe 改名：  Yuhub.exe  ->  Yuhub.exe.bak
2. 新 exe 就位：  <下载的 new.exe>  ->  Yuhub.exe    （此时原路径已空）
3. 启动新的 Yuhub.exe
4. 成功则删掉 .bak（删不掉也无害，下次启动再删）
```

**实测已验证这两步都成功**，且原进程全程不受影响。

比"覆盖写"好在：不需要先把新文件写进被占用路径，因此**不需要**
把 59MB 旧 exe 拷成临时副本再覆盖——省掉一次大文件拷贝。

### 但替换器本身仍不能是目标文件

⚠️ 关键：如果替换器就是 `Yuhub.exe --apply-update` 这个**正在运行**的进程，
那它自己锁着 `Yuhub.exe`，**第 1 步改名会成功、第 2 步「新文件就位到原路径」
也会成功，但它自己已经不在原路径了**——行为会变得难以预期。

所以替换器必须是**一个独立的 exe 副本**，从临时目录运行：

```
%TEMP%\Yuhub_upd_<pid>\Yuhub_updater.exe  ← 从当前 exe 拷一份（或直接拷新版）
     ↓ 启动它，传 --apply-update <base64>
%TEMP%\...\Yuhub_updater.exe --apply-update eyJ...
     ↓ 等旧 PID 死 → 两步改名 → 启动新 exe → 自己退出
```

拷一份的代价：同盘 ~59MB 本地拷贝，亚秒级，可接受。
（也可以拷**新版**当替换器，这样替换逻辑是新版写的；但若新版自身有 bug，
替换器也跟着有问题。**建议拷旧版**，职责单一、行为可预期。）

## 六、状态机（设置页要显示的）

```
IDLE ──检查──> CHECKING ──有新版──> AVAILABLE ──下载──> DOWNLOADING
                    │                    │                  │
                    │                    │              下载完成
                    └──无新版──> UP_TO_DATE                  ↓
                    │                                   READY
                    └──失败──> ERROR ──重试──> CHECKING      │
                                                    点「立即更新」
                                                          ↓
                                              APPLYING（退出自己）
```

UI 文案建议：
- `CHECKING` →「正在检查…」
- `UP_TO_DATE` →「已是最新版本（v0.11.1）」
- `AVAILABLE` →「发现新版本 v0.12.0」+「查看更新内容」+「立即更新」
- `DOWNLOADING` → 进度条 + 速度 + 剩余时间（**直接复用 downloader 的
  `human_speed` / `human_time`，与下载页体验一致**）
- `READY` →「更新包已就绪，重启后生效」+「立即重启并更新」
- `ERROR` →「检查失败：网络不可达」+「重试」

## 七、必须处理的边界情况

1. **更新包下载到一半被中断** → `.part` 文件保留，下次续传（downloader 已支持）。
2. **替换时旧进程还没退干净** → 替换器先 `WaitForSingleObject(pid, 30s)`，
   超时则强行 `taskkill /F`。**不要**只 `sleep(2)` 就动手。
3. **覆盖失败（杀软占用 / 权限不足）** → 先备份 `Yuhub.exe.bak`，
   覆盖失败则回滚并**启动回旧版**，把失败原因写日志。
4. **新 exe 起来就崩** → 替换器启动新进程后 `WaitForSingleObject(5s)`，
   5 秒内退出且退出码非 0 → 判定新版有问题 → **自动回滚**到备份并重启旧版。
   这是"更新把自己搞挂"的最后一道保险。
5. **exe 放在 Program Files（需要提权才能写）** → 复用 `uninstaller.elevation_capable()`
   那套判断；需要时走 `ShellExecuteW("runas", ...)` 拉起替换器。
6. **更新后主题/设置丢失** → 设置存在 `QSettings(HKCU)`，主题在「文档 / Yuhub」，
   **都不在 exe 目录**，所以天然不受影响。这点现有架构已经做对了。
7. **网络不可达 / GitHub 被墙** → 超时 8 秒、静默失败、不弹窗打扰；
   设置页手动点时才显示错误。**检查更新绝不能阻塞启动**。
8. **下载期间用户关程序** → 更新线程要能被优雅取消，`.part` 保留。

## 八、安全（别省）

- **必须校验 sha256**。GitHub API 的 `digest` 字段直接用；拿不到 digest
  就在 Release notes 里手写 `sha256:xxx` 并解析。不校验的话，一个被劫持的
  下载 = 用户机器上跑任意代码。
- **只允许 https**。`normalize_url` 那套要拒绝 http 降级。
- **不要静默自动安装**。已定"静默检查 + 手动触发"，用户点「立即更新」才动手 —
  这既是体验考虑，也是安全底线。
- GitHub API 有速率限制（未认证 60 次/小时/IP），**启动时检查一次足够**，
  别做轮询。

## 九、测试方案（关键：别在真 exe 上第一次试）

沿用项目已有的 `--xxx-selftest` 传统，新增 `--update-selftest`：

```
1. 版本号解析与比较
   "v0.12.0" > "0.11.1" / "0.11.10" > "0.11.9" / 前缀 v 可有可无
2. 用本地 HTTP server 伪装更新源
   http.server 起在 127.0.0.1，返回假的 releases/latest JSON + 假 exe
3. 端到端：下载 → 校验 → 替换 → 重启
   目标 exe 用副本，避免把正在跑的 exe 覆盖掉
4. 失败路径
   - 校验和不匹配 → 拒绝并报错
   - 下载中断 → 续传成功
   - 覆盖失败 → 回滚且旧版仍能启动
   - 新版秒退 → 自动回滚
5. 断电模拟：替换过程中杀替换器，确认旧 exe 仍完整可用
```

**先用本地 `http.server` 跑通全流程**，再切到真实 GitHub Release。
因为替换逻辑一旦出错就是把用户程序搞没，本地可控环境必须先在前面撞完所有坑。

## 十三、实现补充（方案落地时新增的坑）

### 1. ⚠️ `releases/latest` 会跳过 prerelease —— beta 项目必踩

`GET /repos/{owner}/{repo}/releases/latest` 在 GitHub 上的语义是
**"最新的非 prerelease、非 draft 版本"**。本项目 tag 就叫 `v0.8beta`，
发布时勾了 "Set as a pre-release"，结果这个接口直接返回 **404**，
客户端永远检查不到更新（表现为"发布了新版本但没人收到提示"）。

**修法**：`fetch_release()` 改成两级策略 ——

```
① 先试 releases/latest        （正式版走得通，语义最准）
② 404 时退到 releases?per_page=10，取第一个非 draft 的版本
   （prerelease 也认，因为 beta 阶段就是要发 prerelease）
```

自检里加了对应回归项：**「latest 404 时退到 releases 列表」** +
**「draft 版本不被当作更新」**。漏了这条，整个自动更新在 beta 阶段等于没有。

> **后续处置（同日）**：`v0.8beta` 已通过
> `PATCH /repos/{o}/{r}/releases/{id}` 把 `prerelease` 改为 `false`，
> 于是 `releases/latest` 恢复 200，两条路都能通。**两级策略代码保留**——
> 将来若真要发预发布版（如 `v0.9rc`），仍需靠第 ② 级兜底。
>
> 另：Release 页默认**不展示** prerelease（折叠在 "Pre-releases" 区），
> 这是"看起来只有 tag、没有 release"的常见误判来源。注意区分：
> tag 只是 Git 指针、不能挂附件；能挂 `Yuhub.exe` 说明它已是真正的 Release。

### 2. 非 https 地址要放行本地回环

「只允许 https」这条规则会挡住自检——自检用 `http.server` 起在
`127.0.0.1` 上伪装更新源。所以 `_url_allowed()` 显式放行
`http://127.0.0.1` 与 `http://localhost`（回环流量不出本机，无劫持风险），
其余一律要求 https。

### 3. `sys_executable()` 别返回 argv 残留

源码态下 `sys.argv[0]` 可能是 `-c`（用 `python -c` 跑脚本时）。
直接拿它当"要替换的目标"会让替换器去改一个不存在的文件。
改成：`frozen` 时用 `sys.executable`，否则 `argv[0]` 存在且在磁盘上才用，
再退到 `sys.executable`。

### 4. 最终实现的检查项（28 项，`--update-selftest`）

版本比较 6 组 / 版本解析 / asset 挑选 / 检查更新（有新版·已最新·网络不可达）/
**prerelease 兜底** / **draft 排除** / 下载 / 大小比对 / sha256 通过·拒绝 /
摘要错时删半成品 / 拒绝非 https / 两步改名（旧→.bak、新→原位）/ 回滚 /
`apply_update_main` 启动失败自动回滚 / 坏载荷与空路径快速失败。
